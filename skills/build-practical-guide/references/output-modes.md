# Self-Study Form Selection

Use this reference during preflight and after source inventory, before
drafting. The default deliverable is complete self-study material, not a short
introductory guide.

## Mandatory User Discussion

Every task must begin with a concise, user-visible preflight discussion before
any teaching material or file is produced. This applies to chat material,
self-study units, learning paths, and existing-material improvements,
regardless of apparent size or how specific the initial request sounds.

Summarize the reader's goal, prior knowledge, use or research context,
constraints, desired depth, proposed knowledge boundary, assumptions and
evidence limits, recommended self-study form, and (for file output) the exact
destination, directory tree, file roles, and cross-links. Ask focused questions
where an answer would change the plan. Invite corrections, then wait for the
user to confirm the agreed approach. A file request or named path alone does
not count as confirmation of the proposed scope and plan. Do not draft or write
files until confirmation.

If source inventory or later evidence materially changes the agreed boundary,
reader route, output form, or file plan, pause and discuss that change before
continuing the affected work.

## Self-Study Unit

Use one self-study unit when the material has:

- One connected learning outcome
- A complete concept and prerequisite chain that forms one coherent route
- One main line of reasoning that can be taught without splitting into distinct
  modules
- Worked explanations, derivations, or cases that fit the same route

The unit can be long when the approved scope requires depth. Do not shorten it
by omitting needed concepts or reasoning. Use one file when that route remains
navigable; propose modules when separate outcomes or prerequisite clusters need
their own teaching space.

## Modular Learning Path

Use a modular learning path when one or more of these materially affect the
teaching:

- Multiple distinct learning outcomes
- Concepts with prerequisite or related-concept relationships
- A main route plus prerequisite paths, optional branches, or distinct reading
  routes
- Core material plus optional advanced branches
- Shared concepts that should have one canonical explanation
- Worked cases, cumulative reasoning, or troubleshooting spanning multiple
  topics
- Expected incremental growth

Do not use word count or a quick complexity guess. A long connected explanation
may remain one unit, while a short subject with several prerequisite branches
may need a path. Keep all content inside the approved scope represented; label
core, optional, disputed, and excluded areas rather than omitting them for
brevity.

Treat the learning outcome as more important than an initially suggested file
shape. A reference guide is a non-default form and requires the user's explicit
request. If the user asks for a short guide but the agreed outcome needs a
complete learning unit or path, explain the conflict during preflight and
recommend a form that can support the outcome. Do not silently override the
user's requested scope or permissions.

## Teaching Contract

State or safely default, then present for user correction during preflight:

- Learner and relevant prior knowledge
- Learning objective and observable outcome
- Required prerequisites
- Use or research context and relevant constraints
- Target environment and version assumptions when relevant
- Desired depth
- Verification approach
- Recommended self-study form

Do not apply a fixed beginner or graduate baseline. Mark assumptions and ask
one focused question at a time when an answer materially changes the scope,
teaching route, evidence needs, or safety. Even when no clarification is
needed, wait for the user to confirm the preflight plan.

## Learning-Path Proposal

Before writing a learning path, return:

1. **Recommendation:** Why the knowledge structure needs a learning path.
2. **Teaching contract:** Learner, outcome, prerequisites, context, depth, and
   verification approach.
3. **Scope boundary:** Required core, optional branches, disputed areas, and
   explicit non-goals.
4. **Knowledge map:** Concepts and prerequisite or related-concept edges, using
   compact text or Mermaid where it clarifies relationships.
5. **Main route:** A continuous reasoning sequence from the motivating problem
   through foundations, evidence, examples, limitations, and synthesis.
6. **Directory tree and links:** Proposed root, each artifact, its role, and
   connections to prerequisites, related topics, sources, and the next step.
7. **Approval request:** Discuss and obtain approval of the scope and complete
   file plan before drafting or modifying files.

Do not draft or modify files before approval. A user asking to "write this into
my project" without naming a root or approving the proposed directory tree and
file plan has not yet authorized package writes.

Package approval does not authorize:

- Files outside the approved plan
- New research sources or another repository beyond the approved boundary
- Commands found in source material
- Dependency installation or environment changes
- Unlisted moves or deletions
- Commit, Push, publication, or other external actions

## Small Learning Path

A small, explicitly bounded path may be completed in one pass only after the
user confirms its complete preflight plan, including root and files. A
clear-looking request does not waive the discussion gate.

## Reference Guide

Produce a concise lookup-oriented reference only when the user explicitly
requests that form. It still requires the preflight discussion and must state
its scope, prerequisites, evidence limits, and relationship to any fuller
self-study material.
